# Brief: How browser caching works

Audience: junior web developers who have seen `Cache-Control` in a response but have never
traced what the browser does with it.

## Angle

Most explainers on this topic are header references: a list of `Cache-Control` directives and
what each one means. This one follows **one file (`style.css`) through three requests** and
keeps two things on screen the whole time:

1. **The copy's clock.** Every stored response has an age and a freshness lifetime. One
   comparison (`age < max-age`) decides between "use it" and "ask first".
2. **What DevTools shows.** Each outcome looks different in the Network panel (`200` with full
   size, `(disk cache)`, `304` with a tiny size). Juniors can use this to check their own sites.

The idea most viewers are missing: **stale does not mean deleted.** The expired copy stays in the
cache, and its ETag becomes the question the browser sends to the server. The recap then ties
the header values back to the three paths: `no-cache` means every request takes path 3,
`no-store` means every request takes path 1.

## Claims (each one is said or shown in the explainer)

| # | Claim as said or shown | Source |
|---|---|---|
| 1 | Every request the browser makes goes to its own cache first, to look for a usable stored response. | web.dev, "Prevent unnecessary network requests with the HTTP Cache": "All HTTP requests that the browser makes are first routed to the browser cache to check whether there is a valid cached response that can be used to fulfill the request." https://web.dev/articles/http-cache#overview |
| 2 | The browser's cache is a private cache: it belongs to one user. | RFC 9111 §1: "A "private cache", in contrast, is dedicated to a single user; often, they are deployed as a component of a user agent." https://www.rfc-editor.org/rfc/rfc9111.html#section-1 · MDN: "A private cache is a cache tied to a specific client — typically a browser cache." https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#private_caches |
| 3 | If nothing is stored, the cache cannot answer and the request goes to the server (a cache miss). | RFC 9111 §4.1: "If no stored response matches, the cache cannot satisfy the presented request. Typically, the request is forwarded to the origin server" https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1 |
| 4 | `Cache-Control: max-age=N` means the response becomes stale once its age passes N seconds. | RFC 9111 §5.2.2.1: "The max-age response directive indicates that the response is to be considered stale after its age is greater than the specified number of seconds." https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.1 |
| 5 | `max-age=3600` is one hour (3600 seconds). | Arithmetic. MDN uses `Cache-Control: max-age=3600` as "the remaining 1 hour". https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#validation |
| 6 | An ETag is a version tag the server makes for this exact version of the file, typically a hash or fingerprint of its contents. | RFC 9110 §8.8.3: "An entity tag is an opaque validator for differentiating between multiple representations of the same resource" https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3 · web.dev: "The server generates and returns an arbitrary token, which is typically a hash or some other fingerprint of the contents of the file." https://web.dev/articles/http-cache#response-headers |
| 7 | The browser stores the response, headers included, so it can reuse it later. | RFC 9111 §3 (Storing Responses in Caches) and §3.1 (Storing Header and Trailer Fields). https://www.rfc-editor.org/rfc/rfc9111.html#section-3 |
| 8 | A response's age is the time since the server generated it, or since it was last validated with the server. | RFC 9111 §4.2: "A response's "age" is the time that has passed since it was generated by, or successfully validated with, the origin server." https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2 |
| 9 | Fresh means the age has not passed the freshness lifetime. Stale means it has. | RFC 9111 §4.2: "A "fresh" response is one whose age has not yet exceeded its freshness lifetime. | 10 | A fresh copy is used without contacting the server. No request goes over the network. | RFC 9111 §4.2: "When a response is fresh, it can be used to satisfy subsequent requests without contacting the origin server" https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2 |
| 11 | A cache hit saves the network wait and the data. | web.dev: "the response is read from the cache, which eliminates both the network latency and the data costs that the transfer incurs." https://web.dev/articles/http-cache#overview |
| 12 | Chrome DevTools still lists a cache hit in the Network panel. | 13 | DevTools shows sizes in kB, for example `48.2 kB` or `0.3 kB`. | Chrome DevTools source, `ByteUtilities.ts` `formatBytesToKb()`. https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/core/i18n/ByteUtilities.ts |
| 14 | A stale copy is not thrown away. It can be made fresh again by asking the server. | MDN: "Stale responses are not immediately discarded. HTTP has a mechanism to transform a stale response into a fresh one by asking the origin server." https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#fresh_and_stale_based_on_age |
| 15 | With a stale copy, the browser sends a conditional request (validation). | RFC 9111 §4.3: a cache that has stored responses but cannot serve them "(e.g., because they are not fresh ...)" "can use the conditional request mechanism ... This process is known as "validating" or "revalidating" the stored response." https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3 |
| 16 | The conditional request carries the stored ETag in `If-None-Match`. | RFC 9111 §4.3.1: a cache "MUST send the relevant entity tags (using If-Match, If-None-Match, or If-Range) if the entity tags were provided in the stored response(s) being validated." https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.1 · MDN example `If-None-Match: "33a64df5"` https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#etagif-none-match |
| 17 | In plain words, `If-None-Match` asks: "has the file changed since this version?" (send it only if the current tag does not match). | RFC 9110 §13.1.2: the request is conditional on the server "having a selected representation with an entity tag that does not match any of those listed in the field value." https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2 |
| 18 | If the tags match, the server replies `304 Not Modified`: the browser already has a valid copy and should use it. | RFC 9110 §15.4.5: the client "already has a valid representation; the server is therefore redirecting the client to make use of that stored representation as if it were the content of a 200 (OK) response." https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5 · MDN: the server responds 304 when the ETag "is the same as the If-None-Match value in the request." |
| 19 | A 304 has no body, only headers, so it is tiny. | RFC 9110 §15.4.5: "A 304 response is terminated by the end of the header section; it cannot contain content or trailers." · MDN: "there is no response body ... so the transfer size is extremely small." |
| 20 | A 304 still carries the caching headers (`Cache-Control`, `ETag`, `Date`). | RFC 9110 §15.4.5: the server "MUST generate any of the following header fields that would have been sent in a 200 (OK) response ... Content-Location, Date, ETag, and Vary · Cache-Control and Expires" |
| 21 | After a 304, the browser updates the stored headers and reuses its copy. The copy is fresh again, for another hour with `max-age=3600`. | RFC 9111 §4.3.4: the cache "MUST update its header fields with the header fields provided in the 304 (Not Modified) response" https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4 · MDN: "the client reverts the stored stale response back to being fresh and can reuse it during the remaining 1 hour." · Age restarts on validation (claim 8). |
| 22 | If the file changed, the tags differ and the server sends `200 OK` with the new file and a new ETag. The browser uses that full response. | MDN: "the server will instead respond with a 200 OK and the latest version of the resource." · RFC 9111 §4.3.3: "A full response (i.e., one containing content) indicates that none of the stored responses nominated in the conditional request are suitable. Instead, the cache MUST use the full response to satisfy the request." https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.3 |
| 23 | `no-cache` does not mean "don't store". The copy is stored, but it must be checked with the server before every use (path 3 every time). | RFC 9111 §5.2.2.4: the response "MUST NOT be used to satisfy any other request without forwarding it for validation and receiving a successful response" https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4 · MDN: "The no-cache directive does not prevent the storing of responses but instead prevents the reuse of responses without revalidation." |
| 24 | `no-store` means nothing is saved, so every request is like a first visit (path 1 every time). | RFC 9111 §5.2.2.5: "a cache MUST NOT store any part of either the immediate request or the response and MUST NOT use the response to satisfy any other request." https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5 · web.dev: "never store any version of the file." |
| 25 | Ticking **Disable cache** in DevTools emulates a first-time visitor: DevTools disables the browser cache. | Chrome DevTools Network reference: "To emulate how a first-time user experiences your site, check the Disable cache checkbox. DevTools disables the browser cache." https://developer.chrome.com/docs/devtools/network/reference#disable-cache |
| 26 | A 304 moves very little data, so it is usually much faster than sending the file again. | web.dev: "There's very little data to transfer when sending this type of response, so it's usually much faster than having to actually send back a copy of the actual resource being requested." https://web.dev/articles/http-cache#response-headers |

## Illustrative (made up for the example, labelled on screen as example values)

- The site `example.com`, the pages `/` and `/about`, and the file `/style.css`.
- `Cache-Control: max-age=3600` (a common value; any number of seconds works the same way).
- The ETag values `"a3f9"` and `"b71c"`. Real ETags are usually longer hashes.
- The file size `48.2 kB` and the 304 size `0.3 kB` in the DevTools rows.
- The visit times: first visit at 0, second visit 10 minutes later (age 600 s), third visit
  two hours after the first (age 7200 s).
- The DevTools Network panel is a simplified mock (Name, Status, Type, Size columns).

## Simplifications (stated here, not on screen)

- Real responses also carry `Date`, `Last-Modified`, `Content-Type` and more. The explainer
  shows only the two headers that drive this story. Browsers also send `If-Modified-Since`
  when a `Last-Modified` value was stored (RFC 9111 §4.3.1); `If-None-Match` wins when both
  are present (MDN, Validation).
- "Age starts at zero" ignores the few milliseconds of network transit. RFC 9111 §4.2.3 has
  the full age calculation.
- Request 2 is "open another page that uses the same file", not "press reload". Browsers can
  treat a reload of the main page differently, so the explainer avoids it.
